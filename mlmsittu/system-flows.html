F-01

Master system flow

How the four domains connect. Onboarding gates access; procurement fills stock; commerce consumes it; every mutation lands in the audit log.

  V["Visitor"] --> A1["Create account"]
  A1 --> A2["Verify email + mobile OTP"]
  A2 --> A3["Submit business registration
NIC, slip, referrer ID"]
  A3 --> RQ{{"Admin review queue"}}
  RQ -->|approved| BID["Allocate Business ID
compute ltree path"]
  RQ -->|rejected| X["Rejected — reason recorded"]
  RQ -->|resubmit| A3
  BID --> D["Active distributor"]

  S["Supplier"] --> PO["Purchase order"]
  PO --> GR["Goods receipt"]
  GR --> LEDGER[("stock_movement
append-only ledger")]
  LEDGER --> SL["stock_level projection"]

  C["Walk-in customer"] --> SO
  SL --> RES["Reserve stock"]
  SO --> RES
  RES --> PAY["Upload bank slip"]
  PAY --> PV{{"Finance verifies slip"}}
  PV -->|verified| FUL["Fulfil + decrement"]
  PV -->|rejected| PAY
  FUL --> LEDGER

  D -.attribution only.-> REF["referral_summary
direct_count"]
  REF -.-> TREE["Hierarchy + treemap views"]

Scope note — amended 8 Aug 2026. An earlier revision described the referral branch as read-only with no entitlement derived from it. That was recorded in error. The §0.2 reward mechanics are in scope: four stages, one per approved referral, four children maximum, bonus stage on completion. direct_count still feeds views and reports only — stage state is stored and transactionally guarded, never recomputed from a count at decision time, because two concurrent approvals under one parent would otherwise both award the same stage.
F-02

Account creation and verification

Two independent channels. Email uses a signed link; mobile uses a server-stored OTP. Both must pass before login is permitted.

sequenceDiagram
  autonumber
  actor U as Visitor
  participant API as API Gateway
  participant ID as Identity module
  participant R as Redis
  participant W as Worker
  participant EXT as SMTP / SMS

  U->>API: POST /auth/register
  API->>ID: validate + hash password "Argon2id"
  ID->>ID: create app_user "status=unverified"
  ID->>R: store email token + OTP hash
  ID-->>W: enqueue send jobs
  W->>EXT: verification link + 6-digit OTP
  EXT-->>U: email and SMS

  U->>API: GET /auth/verify-email?token
  API->>ID: mark email_verified

  U->>API: POST /auth/verify-otp
  API->>R: constant-time compare hash
  alt code matches
    ID->>ID: mark mobile_verified
    ID-->>U: 200 — login enabled
  else 5 failures
    R->>R: lock 15 minutes
    ID-->>U: 429 OTP_LOCKED
  end
Terminology. Admin 2FA uses TOTP (authenticator app, RFC 6238). Mobile verification uses SMS OTP — a stored random code. Different mechanisms; don't share the implementation.
F-03

Business registration and KYC review

The critical manual path. Claim-based locking prevents two reviewers acting on one record, and every document view is logged for PDPA.

sequenceDiagram
  autonumber
  actor U as Distributor
  participant API as API Gateway
  participant KYC as Onboarding module
  participant S3 as Object storage
  participant DB as PostgreSQL
  actor RV as KYC reviewer

  U->>API: POST /registrations "NIC, images, referrer ID"
  API->>API: validate Business ID check digit
  API->>KYC: verify referrer exists and has capacity
  KYC->>S3: store NIC image + bank slip "SSE"
  KYC->>DB: nic_hash "HMAC" + nic_encrypted "AES-GCM"
  KYC->>DB: status = submitted
  KYC-->>U: 202 pending review

  RV->>API: POST /admin/registrations/:id/claim
  API->>DB: lock to reviewer, status = under_review
  RV->>API: GET document
  API->>DB: write access_log entry
  API->>S3: presigned URL "60s, single use"
  S3-->>RV: image

  alt approve
    RV->>API: POST approve
    API->>DB: BEGIN
    DB->>DB: allocate business_id from sequence
    DB->>DB: compute ltree path from referrer
    DB->>DB: status = active
    DB->>DB: outbox: DistributorApproved
    API->>DB: COMMIT
  else reject
    RV->>API: POST reject "reason enum + note"
    DB->>DB: status = rejected
  else request resubmission
    DB->>DB: status = resubmit_required
  end
Separation of duties. The submitting user can never be the reviewer. Enforce server-side — a client-side check is not a control.

F-05

Business ID allocation and validation

Allocated once at approval, immutable for life. The check digit rejects typos client-side, before a bad parent ID can reach the database.

flowchart LR
  subgraph ALLOC["Allocation — at approval only"]
    SEQ["nextval'business_id_seq'"] --> B32["Crockford Base32
excludes I L O U"]
    B32 --> DAMM["Damm check character"]
    DAMM --> OUT["SLV-8K3M9-4"]
  end

  subgraph VALID["Validation — on referrer entry"]
    IN["User types parent ID"] --> RX{"regex shape ok?"}
    RX -->|no| E1["Reject — malformed"]
    RX -->|yes| CK{"check digit valid?"}
    CK -->|no| E2["Reject — likely typo"]
    CK -->|yes| LOOK{"exists and active?"}
    LOOK -->|no| E3["Reject — not found"]
    LOOK -->|yes| CAP{"under width cap?"}
    CAP -->|no| E4["REFERRER_AT_CAPACITY"]
    CAP -->|yes| OK["Accept"]
  end

  OUT -.stored on distributor.-> LOOK

  classDef err fill:#fdf6f2,stroke:#9c4221,color:#5c3a2a
  class E1,E2,E3,E4 err
Why not a numeric path as the public ID. A path like 1131 is mutable under tree edits, unbounded in length, leaks the full upline, is enumerable, and has no error detection — a typo yields another valid ID and silently attaches the record to the wrong parent. The path is kept internally as ltree and still displayed in admin views.
F-06

Deletion and NIC re-registration

Your rule: a deleted account may re-register with the same national ID. A partial unique index gives exactly that without weakening uniqueness for live records.

flowchart TB
  REQ["Deletion request"] --> ADM{"Admin approves?"}
  ADM -->|no| KEEP["Remains active"]
  ADM -->|yes| TX["BEGIN transaction"]
  TX --> S1["distributor.status = deleted"]
  TX --> S2["set deleted_at = now"]
  TX --> S3["retire business_id — never reissued"]
  TX --> S4["retain financial records
statutory audit period"]
  TX --> S5["schedule document purge"]
  S1 & S2 & S3 & S4 & S5 --> COMMIT["COMMIT"]

  COMMIT --> FREE["Partial unique index no longer
matches this nic_hash"]
  FREE --> NEW["Same NIC may register again"]
  NEW --> HIST["Prior record kept — full history
queryable by nic_hash"]

  classDef ok fill:#e6f0f0,stroke:#0d5c63,color:#0d3f44
  class FREE,NEW ok
Pepper placement. The HMAC pepper must live outside the database — in KMS or the environment. Sri Lankan NIC format is small enough that an unpeppered hash is brute-forceable from a stolen dump alone.
F-07

Procurement to stock

Purchase order through partial receipt. stock_level is never written directly — only the ledger service touches it.

flowchart TB
  SUP["Supplier record"] --> PO["Create purchase order"]
  PO --> LINES["PO lines: item, qty, unit cost"]
  LINES --> SENT["Status: sent"]
  SENT --> ARR["Goods arrive"]
  ARR --> GR["Create goods receipt"]
  GR --> CHK{"Full quantity?"}
  CHK -->|yes| CLOSE["PO line closed"]
  CHK -->|partial| OPEN["PO line stays open
remaining qty tracked"]
  OPEN --> ARR

  CLOSE --> MV["stock_movement +qty
type=receipt, ref=goods_receipt"]
  OPEN --> MV
  MV --> PROJ["Recompute stock_level
same transaction"]
  PROJ --> RL{"below reorder_level?"}
  RL -->|yes| ALERT["Reorder alert to procurement"]
  RL -->|no| DONE["Done"]

  classDef store fill:#e6f0f0,stroke:#0d5c63,color:#0d3f44
  class MV store
Ledger discipline. stock_movement is the source of truth; stock_level is a projection. Any drift is reconcilable by replay. Never UPDATE stock_level outside the movement service.
F-08

Item set availability

Sets are virtual — creating one consumes nothing. Availability is computed on read from the scarcest component.

flowchart LR
  Q["GET /item-sets/:id/availability"] --> L["Load item_set_line rows"]
  L --> LOOP["For each line"]
  LOOP --> AV["available = on_hand - reserved"]
  AV --> DIV["floor'available / line.quantity'"]
  DIV --> MIN["MIN across all lines"]
  MIN --> RESULT["Sets available"]

  MIN --> WARN{"shared component
with another set?"}
  WARN -->|yes| FLAG["Flag contention —
figure is optimistic"]
  WARN -->|no| CLEAN["Figure is firm"]

  classDef warn fill:#fdf6f2,stroke:#9c4221,color:#5c3a2a
  class FLAG warn
The trap. You allowed one item in multiple sets. Two sets sharing a component can each report "available" when only one can actually ship. Availability is advisory; only reservation (F-09) is authoritative.
F-09

Stock reservation

The concurrency-critical path. Deterministic lock ordering prevents deadlock when two orders touch overlapping components.

sequenceDiagram
  autonumber
  participant API as API Gateway
  participant INV as Inventory module
  participant DB as PostgreSQL

  API->>INV: confirm order "lines incl. sets"
  INV->>INV: expand sets to component items
  INV->>INV: sort item_id ASC "deadlock avoidance"
  INV->>DB: BEGIN

  loop each component, in sorted order
    INV->>DB: SELECT ... FOR UPDATE on stock_level
    DB-->>INV: locked row
    alt on_hand - reserved >= required
      INV->>DB: reserved += required
    else insufficient
      INV->>DB: ROLLBACK
      INV-->>API: 409 INSUFFICIENT_STOCK "item, shortfall"
    end
  end

  INV->>DB: order status = confirmed
  INV->>DB: COMMIT
  INV-->>API: 200 reserved
Lock ordering is not optional. Two orders sharing components in opposite sequence will deadlock under load. Sorting by item_id before locking makes it impossible.
F-10

Order to fulfilment

End to end, including the manual slip step. Stock stays reserved — not decremented — until payment clears.

sequenceDiagram
  autonumber
  actor B as Buyer
  participant API as API Gateway
  participant COM as Commerce module
  participant INV as Inventory module
  actor FIN as Finance officer
  actor WH as Warehouse

  B->>API: POST /sales-orders
  API->>INV: reserve stock "F-09"
  INV-->>API: reserved
  API-->>B: order confirmed + bank details

  B->>B: bank transfer, out of band
  B->>API: POST /payments "slip image + bank_ref"
  API->>COM: unique index check on bank_ref
  alt duplicate reference
    COM-->>B: 409 DUPLICATE_SLIP
  else new
    COM->>COM: status = pending
  end

  FIN->>API: GET pending payments
  FIN->>FIN: compare slip against bank statement
  alt verified
    FIN->>API: POST /payments/:id/verify
    COM->>COM: status = verified
    COM-->>WH: release for picking
    WH->>API: POST fulfilment
    API->>INV: reserved -= qty, on_hand -= qty
    INV->>INV: stock_movement -qty
  else rejected
    FIN->>API: POST reject "reason"
    COM->>INV: release reservation
    COM-->>B: resubmit slip
  end
F-11

Payment verification states

Slip-based payment has one dominant fraud mode: one genuine slip submitted against several orders. The unique index closes it.

stateDiagram-v2
  [*] --> pending : slip uploaded
  pending --> duplicate_blocked : bank_ref already used
  pending --> under_check : finance claims
  under_check --> verified : matches statement
  under_check --> rejected : mismatch or unreadable
  rejected --> pending : buyer resubmits
  verified --> released : stock released
  released --> [*]
  duplicate_blocked --> [*]

  note right of duplicate_blocked
    UNIQUE INDEX on payment.bank_ref
    WHERE bank_ref IS NOT NULL.
    Verifier types the reference from
    the image; DB rejects reuse.
  end note

F-13

Request path

Every authenticated request runs this gauntlet. Reads that tolerate staleness are routed to the replica to protect checkout latency.

flowchart LR
  C["Client PWA"] --> CF["Cloudflare
TLS · WAF · rate limit"]
  CF --> LB["Load balancer"]
  LB --> APP["App container"]
  APP --> SES{"session valid?"}
  SES -->|no| E401["401"]
  SES -->|yes| RBAC{"role permits?"}
  RBAC -->|no| E403["403"]
  RBAC -->|yes| IDEM{"POST with
idempotency key?"}
  IDEM -->|replay| CACHED["Return stored response"]
  IDEM -->|new| H["Handler"]
  H --> RW{"read or write?"}
  RW -->|write| PRI[("Primary")]
  RW -->|tolerant read| REP[("Read replica")]
  H --> RD[("Redis — sessions, limits")]
  H --> LOG[("audit_log")]

  classDef store fill:#e6f0f0,stroke:#0d5c63,color:#0d3f44
  classDef err fill:#fdf6f2,stroke:#9c4221,color:#5c3a2a
  class PRI,REP,RD,LOG store
  class E401,E403 err
Replica routing. Send treemap aggregation, hierarchy expansion and report exports to the replica. Never route stock availability there — replication lag causes overselling.
F-14

Outbox and background workers

Side effects are committed as rows in the same transaction as the business change, then dispatched. No lost emails, no phantom sends on rollback.

flowchart TB
  TX["Business transaction"] --> BOTH["Domain write + outbox row
same COMMIT"]
  BOTH --> POLL["Dispatcher polls unsent rows"]
  POLL --> Q["BullMQ queue on Redis"]

  Q --> J1["Send OTP / email"]
  Q --> J2["Retention sweep —
purge expired KYC documents"]
  Q --> J3["Report generation"]
  Q --> J4["Treemap aggregation refresh"]
  Q --> J5["Reorder-level scan"]

  J1 --> RES{"succeeded?"}
  RES -->|yes| MARK["Mark sent"]
  RES -->|no| RETRY["Exponential backoff
max 5 attempts"]
  RETRY --> DLQ["Dead-letter queue + alert"]

  classDef warn fill:#fdf6f2,stroke:#9c4221,color:#5c3a2a
  class DLQ warn
Why the outbox. Sending mail inside a transaction means a rollback still delivers the message. Writing the intent as a row makes the side effect atomic with the change that caused it.
